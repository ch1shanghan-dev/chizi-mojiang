## 3. 从玩家角度规定UI边界

### 3.1 信息露出

| 层级 | 应当出现的信息 | 呈现方式 |
| --- | --- | --- |
| 当前决策 | 手牌/筹码/行动、轮到谁、操作费用、真实余额、结算结果、影响继续游玩的保存状态 | 清楚、简短、直接可见；沿用已有余额与壳入口，避免重复占位 |
| 目标与内容 | 当前成就条件/资格、必要进度、少量近期目标、角色关系与相关剧情 | 内容为主；先展示当前有用的条目，分类/搜索/分批展开，避免一次铺满10000条 |
| 按需详情 | 达成时间/模式、完整条件说明、次要统计、奖励明细、历史回忆 | 在确有需求时展开或进入详情；已有功能保留可达，但不要求每行永久堆满全部字段 |
| 异常处理 | 是否保存、是否扣款、能否安全离开、下一步怎样恢复 | 直接说明实际后果与可行动作；必要时提供详情，不只显示一个含糊错误码 |
| 开发诊断 | 存储键、ACK/CID/epoch、原始JSON、文件路径、堆栈、数据库与测试用例、质量审查状态 | 开发工具或主动打开的诊断详情；普通游玩流程不展示 |

“已解锁6/1453”是有用的收藏进度，可以显示；“1946条原始定义、自然合格数未审定、E69通过”属于开发报告。费用、带入风险、未保存结果不能因为“信息太多”而隐瞒。

### 3.2 UI不能僭越

- 展示层不得自行发奖、重算收益、修改成就条件、清存档，或将按钮渲染完成当成交易成功。真实状态仍来自既有规则、钱包及确认结果。
- 装饰、成就通知、剧情和普通提示不得抢占关键行动、强制暂停牌局、反复夺焦点或盖住结算。高风险离场、付款和不可逆操作保留必要确认；筛选、排序等可逆操作不追加确认。
- 扩展UI限定在自己的根节点与层级；不覆盖宿主无关菜单、选择器和热键，不为强调自己而增加全局遮罩或更高层级。
- 正文、牌面和操作区优先；标题/导航精简。正文至少12px、主要触控目标至少44px，不能缩小文字和点击范围凑面积。
- 矮横屏允许折叠低频设置与次要说明。关键行动和风险保留常驻；“所有信息必须同时可见”不再是目标。
- 每加一个常驻控件，先说明它帮助玩家做什么决定；可以复用现有入口或按需详情的，就不另造一排按钮。
- 通知节制、动效可跳过/减少、声音尊重现有偏好。艺术品质通过构图、字阶、材质、留白和反馈节奏改善，不靠放大标题、堆金边或发光面积。

## 4. 必要关键检验：按改动风险选择

不设固定测试数量、截图数量、代理数量或审查轮数作为完成标准。先指出本次可能出错的关键点，再选覆盖这些点的现有工具或最短可复现流程。

| 改动级别 | 最小必要检查 | 不默认做的事 |
| --- | --- | --- |
| 文档/方案 | 核对变更事实、相关引用与差异格式 | 不跑游戏、世界模拟、全仓哈希或另请多名代理复核 |
| 展示/文案/搜索/排序 | 检查目标行为与重要边界；相关界面点通。涉及布局时一次桌面和一次手机横屏，矮屏改动补640×286；涉及配色才扩到六皮肤 | 不因单行文案改动重跑全模式、自对弈、所有页面/皮肤和存档迁移；不新增与实现一一照抄的测试 |
| 事件采集/状态/AI策略 | 正常路径加本次关键反例；按需覆盖归属、取消、重复、旧局/控制权等实际风险；验证真正使用的宿主接口 | 不穷举无关模块、所有角色和所有状态组合；不为追求理论最优或永远零不确定性停工 |
| 金钱/存档/迁移/结算/更新/服务器写入 | 相关正确性检查及关键失败/重试/重复/恢复路径；确认金额、持久结果、旧档和唯一兑现；在隔离数据/安装中验证 | 不省掉实际扣款/到账、幂等或可恢复性的检查，也不对真实玩家档/生产做破坏性试验 |

补充执行规则：

1. 一个稳定实现验证一次；修改影响到已验结论、检查失败或出现新证据时，再补相关复验。
2. 多个改动合成候选批次、共享基础层变更、较高风险交付时跑一次完整门禁。世界模拟用于世界逻辑/相关耦合或候选批次检查，不因每个HTML文本改动强制运行。
3. 优先复用现有工具并合并相近场景。短期一次性调查不必都升级成永久门禁或新脚本；只有关键、易复发且维护成本合理的缺陷进入长期回归。
4. 代理作者自检后由主代理做必要集成；跨模块事务、复杂采集和高风险修复再选一名独立复核。避免对同一低风险改动重复开数名审查代理。
5. 未验证的设备/机制如实列出，安排相关验收；不宣称通过，也不无条件阻塞不依赖它的功能。影响钱、存档或正常操作的已知缺陷仍要修或暂停相关交付。
6. 关键错误不能通过删测试、放宽真实正确性断言、吞异常或伪造数据变成通过；“减少不必要检查”不等于降低核心正确性。

这些规则取代旧文档中对每个小节点一律全套正常/失败/重试/关闭/旧档/截图/双重审查的要求。具体检查要与实际改动匹配。
