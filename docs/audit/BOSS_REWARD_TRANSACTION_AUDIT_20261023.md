# 既有 BOSS 特殊奖励事务只读审计 · 2026-10-23

范围：只读当前 `core/csh_bossrecord.js`、`core/csh_wallet.js`、`core/csh_migrate.js` 及 `skills/boss.js` 的记录调用。仅新增本报告，不修改运行源码、AI、战斗规则或玩家存档，不提交或发布。下文是源码证据与待实施设计；没有将设计当成故障注入或自然对局验收结果。

## 结论与证据

现有 `wallet.bossSaved` 已解决记录跨同名 ZIP 的保全，但没有将记录与特殊收益组成事务。当前仍存在“计数/每日资格已消费，货币未保存，日志却报全额”的窗口。

| 位置/真实调用 | 已确认行为 | 缺口 |
| --- | --- | --- |
| `csh_bossrecord.js:74` `saveConfigCopy`；`:510` 附近 `csh_wallet.preserveBoss` | 先将 `bossSaved` 严格写入钱包，再向宿主 config 作兼容镜像；config 镜像不决定保全是否接受 | 这一步没有包含该事件的 CBY、功勋债务或领取收据 |

实际数值与口径：`REWARD_FIRST` 为 elite 500、lord 1200、ultimate 3000、egg 800；`REWARD_DAILY` 为 200/400/800/300。daily 用整个讨伐记录的 `s.lastDaily`，是**全体魔王每天一次**，并非每只每天一次。妖灵挑战者及应战两场景都为 **800 CBY + 基础 25 功勋**，每击破一次即时结算，不要求最终胜利。应战主 BOSS 战绩本身目前无上述首杀/每日奖励，不能借修事务新增奖励。

限额在真实钱包定义：CBY 总余额上限 `100000000000`；功勋每日软上限 `300+当前官阶×10`，超出部分 ×0.5，官阶≥40时先 ×0.6，最后向下取整。妖灵基础 25 因而不等于实际 25：低阶且完全溢出时 12，高阶未溢出时 15，高阶完全溢出时 7。余额只剩 100 空间时 800 名义额最多实际入账 100。

## 最小可行设计：钱包一次提交，官阶一次补偿

建议保留现有两后端，不引入新数据库。实现集中于钱包的私有讨伐结算协调器，记录模块只提供经白名单和常量推导的事件，宿主 config 改为已确认快照镜像。不能继续“先调用 `preserveBoss`，再另外发钱”。

1. **识别一次真实事件。** 观察层将当前死亡事件传入非战斗记录适配器。用 WeakMap 把该事件对象映射为内部 token；同一事件的重复回调复用 token，复活后的新 `die`/`dieAfter` 事件得到新 token。主 BOSS 保留原有 over/dieAfter 的收尾互斥，只在钱包阶段接受后占 `_cshBossRecorded`。不要把玩家对象或 `runId+minionId` 当 token。新增参数只是观察上下文，不改技能 filter、触发、伤害或复活机制。
2. **串行准备与提交。** 钱包协调器按观察事件顺序处理，内部生成 `origin+seq`，其中 origin 为本份新事务账本的随机来源 ID，seq 单调递增。金额、档位、是否首杀、是否 daily、妖灵场景均由已验证事实推导；补领接口无金额参数。未提交事件可在当前页面内存保留并提示失败；钱包写失败时不得前进序号、占记录/每日/观察哨兵或向后处理成同一个序号的新事件。新事件排队，不能替换失败事件。
3. **同一个 `localStorage.setItem(K_WALLET,...)` 提交完整 nextWallet。** 内容必须包括更新后的 `bossSaved.bossKill`（n/first/last/best、全局 lastDaily）、命中悬赏时的 `bossSaved.bounty` 清空、实际 CBY 增量、pcPeak/交易链、新事务序号/资格收据、待写流水，以及待补官阶的基础额和事件事实。先构造副本，严格写成功才替换内存。CBY 实得为 `min(名义额,余额剩余空间)`；首杀与 daily 在同一事件内合并一个事务，分别保留明细。余额封顶时仍确认真实击破并记录实际 0，不把余额上限变成自动隐藏债务。
4. **官阶提交与收据同写。** 新增私有 `settleBossMerit` 路径，只处理钱包中已确认、尚未完成的 intent，禁止外部提供新奖励。复制 rankData，按当前正式功勋公式计算 actualMerit，**同一次严格写 K_RANK** 保存 merit、meritToday、rank 及该事务完成凭据；成功后才替换内存/播放晋阶提示。写失败不改内存、不返回成功，钱包中的 intent 保留，启动后或无参重试自动补官阶。rank 已写、钱包清 intent 前崩溃时，rank 凭据阻止再加功勋。
5. **明确功勋日期。** 最小方案沿用 `claimPool` 的处理口径：功勋以“第一次成功提交官阶”的当天、当时官阶和剩余软额度计算，成功收据冻结实际值，重试不再计算。失败前的估计不能打印为已得。跨日补领会使用补领当天的额度；它不是追补到旧日。如果要强制按击破当日额度，必须扩展所有功勋入口的预约额度账，不应通过只冻结名义 25 来假装解决。本设计不引入这一额外经济规则。
6. **后处理均可重试。** 已确认记录向宿主 config 同步，流水按 txId 幂等写入；失败保留各自 intent，不重发 CBY。好感度继续作独立、已接受记录之后的表现/互动副作用。不可让镜像/好感度失败反向取消已确认 CBY，也不能在重试时再次增加击破 n 或热度。

建议的最小新增数据形状：

| 所在键 | 字段 | 目的 |
| --- | --- | --- |
| 钱包 | `bossRewards:{v,origin,committedThrough,legacyConsumed,firstConsumed,dailyConsumed,pending[]}` | 累计已提交序号、兼容旧资格、未完成功勋/镜像/流水意图；pending 内包含 seq、角色、事件类型/场景、基础额、实际 CBY、时间和后处理阶段 |
| 官阶 | `bossRewards:{v,origin,appliedThrough,...}` | 与 merit 同次写入的幂等凭据及待回传实际收益；必须可确认钱包 pending 的 seq 是否已应用 |
| 流水 | `bossTx` | 按交易 ID 防止恢复时重写同一笔显示流水 |

为避免每次妖灵击破永久增加一条已完成记录，按 origin 顺序处理并维护连续完成水位；若魔王 CBY 事件没有功勋，也须以 0 功勋确认序号或采用等价的明确跳号方案。只有两侧确认且必要流水恢复完成，才能压缩该 pending 明细；未完成项不得按“最近 N 条”裁掉。序号≤已提交水位的旧 token 只能返回 already，不能再次入账。遇到损坏序号/来源不匹配时拒绝支付并保留数据，不能当作空账重建。这个水位方案的前提是单实例串行协调器；若允许多个宿主同时写同一存储，应另外引入互斥，不把 HMAC 当并发锁。

返回/日志建议区分 `recordCommitted`、`gained`、`meritGained`、`meritPending`、`mirrorPending`、`ledgerPending`、`already`。钱包阶段成功、官阶失败是“讨伐已记录，实得 X CBY，功勋待补领”；完整成功才说实际 Y 功勋。余额封顶要写“本次实得 0 CBY（余额已满）”，不可固定报 +800。热度从已提交后的 n 推导首破 1.5%/重复0.3%、最终上限50%，不要另存一份可重复加的热度余额。

## 旧档、ZIP、部分导入与回滚

**不能从旧计数推导欠奖。** 旧格式没有能证明是否已兑现的收据。首次启用只将当前 n>0 的魔王首杀、当前 lastDaily 记为 legacyConsumed，保持余额、功勋和次数原样；妖灵旧 n 完全不生成 pending。此后只有新观察事件产生新 intent。用户旧档可能曾漏发，但没有证据不能补 `n×800` 或重发所有首杀。

保留新首杀/daily资格凭据与展示次数分离：只导入一份更低计数的 bossKill 不应让本机已兑现首杀再次可领。旧档导入中出现的正计数和 lastDaily 可扩充“历史已消费”基线，不能生成收益。daily 继续沿用当前本地日历语义，不顺手改成每 BOSS 或 UTC 日期。

现有迁移证据与必须补齐的点：

- `collectBody()` (`csh_migrate.js:1049` 起) 已优先将钱包 bossSaved 扁平化回 bossKill/bossAsBoss/bounty；同名 ZIP 删除 extension_* 后钱包保全副本仍在。新事务元数据放在钱包/官阶，不能只放 extension_* config。
- 当前 `cleanWallet` / `cleanRank` (`:343` / `:362` 附近) 只有已列字段，新事务字段会被丢弃。必须同时新增严格清洗器及来源/序号/金额/水位一致性校验；不能遇到损坏 pending 就静默清空。
- 当前 `cleanLedger` (`:928`) 仅保留 t/d/r/c/b，会剥掉交易 ID。若依靠 `bossTx` 恢复流水，要同步保留并校验此字段，或在导出时将已确认流水和未完工任务显式分离，不能既剥 ID 又重新补同一流水。
- 当前部分导入计划 (`:1238` 起) 会把选中讨伐域重新合入钱包；钱包单独导入又保留本机未指定讨伐域。这对纯记录保全成立，对带未完成功勋债务和水位的新事务不足以保证一致。
- `commitPlan`/`restoreJournal` (`:1295` 起) 已保存所有计划内原始 LS/config/内存，失败恢复，并 `reloadModules` 同批采用钱包、官阶。新涉及的键必须同时进入 plan/journal；恢复标志清理之前禁止启动补奖循环，重新采用快照时丢弃旧内存事件 token。

建议采用下表的最小安全部分导入规则，明确拒绝无法证明同一事务快照的混搭；不要为了保持入口看似成功而默默重放：

| 操作 | 建议行为 |
| --- | --- |
| 完整新格式行囊导出/导入 | wallet、rank、bossKill 与新事务元数据按同一经济快照导出；真实欠付官阶 intent 必须携带，已完成流水可扁平化；导入校验后一次 journal 应用，导入本身不创建新击破 |
| 仅导入讨伐记录 | 保留本机钱包金额/功勋/事务水位/未完成 intent；将外来历史作为展示和已消费资格基线，无任何追溯发奖；更新后的钱包副本及config同入plan/journal |
| 仅导入钱包或仅导入官阶，且涉及新事务来源/水位/债务变化 | 在任何写入前拒绝，说明需一并选择钱包、官阶、讨伐记录。若以后要允许，只能另做一致性重建策略；不能套用“保留另一个域”直接通过 |
| 新格式回滚 | 钱包金额/CBY凭据、官阶功勋/官阶凭据、bossSaved及相关config一并恢复同一备份；仅回滚展示记录沿用上一行“记录单域”策略 |
| 导入旧格式、没有新事务信息 | 作为历史导入建立“不追补”的 legacyConsumed；若要覆盖本机新经济账，必须完整选择经济域并明确替换快照，不能用缺字段默默清 pending |
| 重置/卸载及启动恢复 | 重置按同一域完整删除；恢复未完成 journal 优先于补奖。不得由启动默认值把旧 receipt/旧pending复活 |

完整旧快照回滚也会恢复旧余额和旧资格，这是本地存档的既有回滚语义，不能声称具备跨设备/历史备份不可回滚的反作弊保证。此方案保证一次采用的快照内部一致，不建立外部不可撤销账本。

## 行为验收清单（待实施后执行）

必须执行真实钱包/官阶函数、隔离 localStorage 和真实宿主 config 后端；不访问玩家 profile。观察事件和存储故障注入可用固定夹具，但自然 BOSS 流程需另测。

1. 四档魔王首次击破：记录n、首杀、当天全局daily同次钱包提交；同日另一魔王只发该魔王新首杀，不重复daily。旧首杀新一天只发daily。应战胜/负保持既有战绩与特殊奖励政策。
2. 同一妖灵挑战者/应战分别每次800+基础25；同局同玩家对象复活再死两次应累计n+2、CBY+1600、功勋按两次真实公式结算。对同一个死亡事件回调两次只结一次；双监听/双收尾相同事实只接受一笔。
3. 钱包严格写失败：n/lastDaily/bounty/CBY/receipt/功勋均不变，允许同事件重试。不得提前占 `_cshBossRecorded`；UI显示失败。恢复后成功只一次。
4. 钱包写成功后立即崩溃：重启读取n和CBY都已提交，补功勋恰一次；绝不再次增加n或800。钱包写成功、rank写失败不假报25。
5. rank写成功后钱包清intent失败/进程退出：重启检查rank收据，仅确认完成不再加功勋。rank写失败返回结果必须不是ok:true，且内存rank不改变。
6. CBY余额距封顶100时只实得100，已满时实得0；记录仍确认；事务、流水与日志显示actual。低阶软额度足/跨界/已满及≥40级三种功勋折价逐项核对；如跨日重试按文档的成功提交日政策计一次。
7. 流水写失败、config IDB事务拒绝、config完成回调迟到：经济收据/记录保留，镜像/流水可重试且不重复；日志不可将镜像pending说成全链路完成。
8. 妖灵悬赏命中时n、CBY与清悬赏同次钱包提交；失败不清悬赏，成功不因 config 镜像未写而再次出战同一指定目标。热度只由提交次数推导。
9. 大量重复妖灵击破超过历史缓存长度后，早期重复token仍不可支付；未完成功勋/流水不被截断；损坏来源/seq/pending拒绝继续发，不重置成空账。
10. 带旧n/lastDaily无新收据的存档启用功能、关闭重启、导出导入，均不增加旧奖励；仅新击破触发。先前已付记录不得因记录单域低计数导入重新获得首杀。
11. 真正同名ZIP安装清理extension_*后，bossSaved、新事务水位、余额、功勋均保留；待补功勋最多一次。不是仅手工删配置键就声称安装流程通过。
12. 完整导入、仅记录导入、仅钱包/仅官阶拒绝策略、旧格式导入、回滚、重置逐项覆盖。对LS第N键写失败、IDB事务失败、内存采用失败分别检查原始journal恢复；恢复期间无补奖，旧会话迟到回调不得写入新快照。
13. 真实 BOSS局实际击破妖灵、复活后再破、最终胜/负都观察到账；同时开启新的普通对局CBY时，终局基础奖励与即时妖灵特殊奖励各走自己的事务，均不被误去重，不破坏原胜负统计和BOSS收尾返回值。

建议实施文件仅限 `core/csh_wallet.js`（协调器/严格官阶凭据/启动补偿）、`core/csh_bossrecord.js`（改为原子事件提交及真实收益日志）、`core/csh_migrate.js`（元数据与经济域一致性）、`skills/boss.js` 的非战斗观察调用参数（传当前事件、接受后占标记），加隔离探针及报告。所有战斗规则和AI保持原样。当前报告未作这些运行改动。
