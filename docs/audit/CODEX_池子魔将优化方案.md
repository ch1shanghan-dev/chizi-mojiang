# 池子魔将：Codex 代码审查与优化方案

> **用途：** 将本文档放在「池子魔将」仓库根目录，并交给 Codex 执行。\
> **总目标：** 在尽量保留现有玩法、技能设计和兼容性的前提下，改善 UI
> 可读性，审查武将技能 AI
> 配置，并验证每个功能模块是否真正实现了预期行为。\
> **基本原则：先理解，再修改；先定位证据，再修复；每批修改都要验证。**

------------------------------------------------------------------------

## 一、项目目标与工作边界

本次工作聚焦三个方向：

1.  **UI 视觉与可读性**
    -   目前部分界面设计不够理想，部分字体存在明显光晕、发光、阴影或描边叠加，导致文字边缘模糊、内容难以辨认。
    -   需要统一视觉层级、文字清晰度、颜色对比度、间距和组件风格。
    -   优先处理可读性问题，不以增加特效为目标。
2.  **武将技能 AI 配置质量**
    -   检查技能代码中的 `AI: { ... }` 是否正确、合理、完整。
    -   不得简单地以"有没有 `AI` 字段"判断质量。部分技能可能依赖默认
        AI、触发时机或其他配置，并不一定需要单独增加 `AI` 对象。
    -   需要结合每个技能的实际机制、发动代价、目标合法性、收益、限制条件和无名杀当前版本的
        API 判断。
3.  **功能模块的实际正确性**
    -   盘点仓库中的所有模块、菜单项、设置项、弹窗、按钮、技能、数据读写和跨模块调用。
    -   对照
        README、注释、翻译文本、设置描述和现有实现，判断功能是否符合其设计意图。
    -   找出"界面有入口但实际不生效""只在特定条件下生效""状态显示与真实状态不一致""模块之间相互影响"等问题。

### 工作边界

-   不推倒重写现有架构，不为追求代码风格而大规模重构。
-   不擅自修改武将技能的核心设计、数值、触发条件或游戏平衡。
-   不删除现有功能、资源、兼容逻辑或历史配置，除非确认其无用且有充分依据。
-   不引入新的第三方依赖，除非确有必要，并说明原因。
-   不把未经运行验证的功能描述为"已经完全正确"。
-   对于无法通过静态代码判断的游戏内行为，必须明确标注"待实机验证"。
-   保持项目现有的编码风格、目录结构、命名习惯和无名杀版本兼容策略。

## 二、执行前：先摸清仓库，不要立即改代码

开始修改之前，先完成仓库盘点。

### 2.1 检查仓库状态

1.  确认当前仓库根目录、当前分支和项目结构。
2.  查看 Git 工作区状态，识别已有的未提交修改。
3.  不覆盖、不重置、不清理用户已有的改动。
4.  阅读
    README、更新日志、扩展入口、配置文件、依赖说明和项目内的开发文档。
5.  确认项目实际支持的无名杀版本、运行环境及扩展加载方式。
6.  如果仓库中有测试、格式检查、构建脚本或类型声明，先了解其使用方式。

### 2.2 建立项目结构清单

扫描实际存在的目录与文件，不要假定项目一定采用某一种结构。重点识别：

-   扩展入口和初始化流程；
-   武将定义、技能定义及技能翻译；
-   UI 页面、弹窗、菜单、按钮和交互组件；
-   CSS 样式、主题、字体、阴影和动效；
-   配置读写、存档、缓存和状态同步；
-   公共工具函数、事件监听器、钩子及兼容代码；
-   图片、音频、字体等资源；
-   网络请求、外部依赖和跨模块调用（如果存在）。

输出一份模块清单，至少包括：

  字段         说明
  ------------ ------------------------------
  模块名称     使用项目里的真实名称
  文件路径     标明实际文件，不要猜路径
  主要职责     说明它负责什么
  入口与依赖   从哪里调用、依赖哪些模块
  关键状态     读取或修改哪些数据
  初步风险     高、中、低，及判断依据
  验证方式     静态检查、模拟测试或实机测试

**阶段产物：** 在仓库根目录生成
`CODEX_AUDIT_REPORT.md`，先写入项目结构、模块清单和初步发现。若仓库已有同类审查文档，应优先更新现有文档，避免重复创建。

## 三、UI 优化：以清晰、统一、稳定为第一优先级

### 3.1 定位文字光晕和模糊的来源

全仓搜索并检查可能造成文字发虚的样式，包括但不限于：

-   `text-shadow`
-   `filter: blur(...)`
-   `filter: drop-shadow(...)`
-   `-webkit-text-stroke`
-   `text-stroke`
-   多层叠加的阴影、描边和伪元素光效
-   透明度过低的文字、渐变文字及背景混合效果
-   过强的发光动画或重复应用的滤镜
-   全局 CSS 选择器意外影响游戏本体界面

不要看到 `text-shadow`
就全部删除。先判断它作用于标题、装饰字、正文、按钮、提示信息还是状态标签，再决定如何调整。

### 3.2 文字样式优化原则

-   **正文和技能描述优先清晰可读。**
    普通文字原则上不使用强光晕、多层发光和过粗描边。
-   文字颜色与背景要有足够对比度，尤其关注暗色背景、半透明面板和复杂图片背景。
-   标题、正文、辅助说明、数值、按钮文字应有明确的字号、字重和颜色层级。
-   避免使用过细字体、过小字号或过低透明度呈现重要信息。
-   装饰性发光只保留在确有视觉意义的少量元素上，并控制强度和扩散范围。
-   不要为了"统一"而让所有文字变成同一字号、同一颜色或同一字重。
-   优先使用项目现有字体和资源；没有必要时不要额外加载网络字体。
-   中文、数字、标点、技能名称和长描述都要检查，避免截断、重叠、溢出和换行异常。

### 3.3 建立可维护的样式规范

在理解当前样式结构后，尽量复用现有主题变量；若没有合适的统一变量，可在局部样式范围内建立少量设计变量，例如：

-   正文颜色、辅助文字颜色、标题颜色；
-   面板背景、边框颜色；
-   正文阴影强度、标题装饰强度；
-   常用间距、圆角和层级；
-   强调色与危险状态色。

不要为了引入设计规范而进行无必要的全仓 CSS
重构。优先使用清晰、局部、可回滚的改动。

### 3.4 防止污染无名杀本体 UI

-   优先使用扩展专属的根容器、命名空间或限定选择器。
-   避免无范围限制的 `div`、`span`、`button`、`p`、`*` 等全局样式。
-   检查是否修改了无名杀本体的技能提示、卡牌文字、菜单、弹窗或其他扩展的
    UI。
-   如果某些样式确实需要作用于本体界面，必须明确记录影响范围，并验证副作用。
-   保留必要的兼容样式，不因局部美化破坏旧版本布局。

### 3.5 UI 验收标准

至少检查以下情况：

-   扩展主界面及主要子界面；
-   武将名称、技能名称、技能描述、按钮、设置项和提示文本；
-   普通状态、悬停状态、选中状态、禁用状态、警告状态（项目存在时）；
-   长文本、窄窗口、不同缩放比例和移动端布局（项目支持时）；
-   浅色或深色背景（项目存在相应主题时）；
-   UI 关闭、重新打开和切换页面后，样式与状态仍然正常。

验收要求：

1.  主要文字在正常使用尺寸下清晰，不存在明显影响辨认的强光晕或模糊边缘。
2.  重要文字与背景有足够对比度。
3.  没有明显的文字重叠、裁切、溢出或按钮不可点击问题。
4.  扩展外的无关界面没有被意外改变。
5.  视觉效果没有明显退化；需要保留的装饰效果仍然存在，但不能压过文字本身。

如果无法启动游戏或无法截图验证，应提交代码级检查结果，并明确列出需要用户实机确认的页面，不能声称已完成全部
UI 验收。

## 四、逐个审查武将技能中的 `AI: {}`

### 4.1 先建立技能总表

从实际代码中提取所有武将与技能，建立以下信息：

-   武将 ID、技能 ID；
-   技能类型：主动、触发、锁定、觉醒、限定、使命、转换、视为、响应、装备相关或其他实际类型；
-   触发时机、发动条件和发动代价；
-   是否涉及选牌、选目标、响应、使用牌、伤害、回复、摸牌、资源变化或状态标记；
-   当前是否配置 `AI` 相关字段；
-   相关辅助函数、技能组合、子技能和全局技能；
-   需要重点审查的原因。

技能类型应依据实际代码判断，不要只根据技能名称或描述推断。

### 4.2 审查 AI 配置的正确性与适用性

逐项检查适用的 AI
配置及相关逻辑。具体字段以项目当前使用的无名杀版本和实际引擎实现为准，不要假定所有版本都完全相同。

重点关注：

1.  **发动时机与收益判断**
    -   AI 是否在有收益时合理发动技能？
    -   是否会在明显无收益、负收益或不符合条件时浪费技能？
    -   是否遗漏必要的发动条件或状态判断？
    -   强制触发、自动触发和主动发动是否被正确区分？
2.  **选牌逻辑**
    -   选出的牌是否满足技能要求？
    -   是否正确处理手牌、装备牌、特殊区域、虚拟牌和不可选择的牌？
    -   是否考虑牌的使用价值、保留价值、花色、点数、类型及技能代价？
    -   是否会反复选择无效目标，或错误地交出关键牌？
3.  **选目标逻辑**
    -   是否考虑目标合法性、距离、次数、阵营、身份、存活状态和技能限制？
    -   是否区分敌人、队友、中立对象及身份不明的对象？
    -   是否考虑目标的体力、手牌、装备、状态、免疫效果及可能的反制？
    -   是否会对队友使用有害技能、对敌人使用治疗，或选中无法成为目标的角色？
4.  **伤害、回复与收益评估**
    -   是否考虑伤害来源、伤害属性、护甲、减伤、免疫和替代效果？
    -   是否合理评估回复、摸牌、弃牌、控制、转移伤害和资源交换？
    -   是否存在对伤害结果估计错误、重复计算收益或忽略技能副作用的问题？
    -   多段效果、连锁、转化和延迟结算是否需要单独分析？
5.  **技能协同与状态变化**
    -   是否依赖其他技能、标记、临时状态、次数限制或回合阶段？
    -   状态发生变化后，AI 是否仍使用旧判断？
    -   子技能、隐藏技能、组合技和全局技能是否被遗漏？
    -   是否会出现技能看似可以发动，但执行后没有实际效果的情况？
6.  **特殊场景**
    -   没有合法目标、没有可用牌、资源不足、濒死、死亡、回合结束等边界条件；
    -   技能被封锁、禁用、替换或临时获得、失去的情况；
    -   多人、多目标、身份未知、联机或不同模式下的行为（若项目支持）；
    -   其他扩展或本体技能介入后的兼容性。

### 4.3 判断 `AI: {}` 是否"足够完善"

不能简单地要求每个技能都增加更多 AI 字段。应按技能实际需要分类：

-   **无需额外 AI 配置或依赖默认行为：**
    说明原因，并检查默认行为是否足够。
-   **已有 AI 配置且合理：** 保留，记录关键判断依据。
-   **已有 AI 配置但存在问题：** 指出具体字段、条件或逻辑错误，并修复。
-   **缺少必要 AI 逻辑：** 结合技能机制补充最小且正确的实现。
-   **静态代码无法确定：** 标记为"待实机验证"，列出触发条件和观察方式。

特别注意：

-   不要为所有技能机械地补上同一套 `order`、`result`、`effect`、`check`
    或其他 AI 字段。
-   不要凭空添加当前引擎不支持的字段，也不要只凭字段名称猜测其语义。
-   先确认当前版本的 API、仓库中的类型声明、已有同类技能和可用参考实现。
-   对 AI 评估函数中的返回值、参数、执行上下文和副作用进行核查。
-   AI 逻辑应与真实技能结算保持一致，不能让 AI
    的预测与技能实际结果脱节。
-   不要只以"AI
    能发动技能"作为通过标准；还要检查是否在正确的时机、对正确的对象、以合理的代价发动。

### 4.4 AI 审查结果格式

每个发现至少记录：

  字段          内容
  ------------- ------------------------------------
  武将 / 技能   真实 ID 与可读名称
  文件位置      文件路径和相关代码位置
  当前行为      根据代码可确认的行为
  预期行为      根据技能描述、注释和机制得出的预期
  问题与证据    具体条件、代码片段或调用关系
  严重程度      P0 / P1 / P2 / P3
  建议修复      最小必要改动
  验证方法      场景、预期选择和实际结果
  验证状态      已静态确认 / 已测试 / 待实机验证

## 五、模块功能审查：检查"是否真的按预期工作"

### 5.1 为每个模块建立功能契约

不能只看代码是否能运行，还要明确每个模块应该做什么。

对每个模块回答：

1.  模块的入口在哪里，什么时候被调用？
2.  用户如何触发它？是否存在隐藏条件？
3.  输入数据来自哪里，格式和范围是什么？
4.  它会读取、修改或持久化哪些状态？
5.  正常情况下应产生什么结果？
6.  失败、空数据、重复调用或中断时应如何处理？
7.  它依赖哪些其他模块？依赖失败时会怎样？
8.  是否存在异步操作、事件监听器、定时器或缓存？
9.  用户界面展示的状态是否与内部真实状态一致？
10. 是否有明确方法验证功能成功，而不是只看到按钮或提示？

以
README、技能说明、注释、设置描述、现有实现和历史提交为依据。若这些资料互相矛盾，不要自行假设其中一个必然正确，应在报告中标注冲突。

### 5.2 重点检查的通用问题

-   入口或事件监听器没有正确注册；
-   函数存在但从未被调用，或调用时机错误；
-   设置开关只影响 UI，没有真正影响业务逻辑；
-   设置保存了但读取时未生效，或重启后丢失；
-   数据更新后界面没有刷新，或刷新时使用旧状态；
-   变量作用域、异步顺序、重复监听和资源释放问题；
-   缺少空值、非法数据、角色死亡或特殊阶段等边界处理；
-   多次触发导致重复结算、重复弹窗或状态累积；
-   模块 A 修改的数据与模块 B 读取的数据格式不一致；
-   兼容代码掩盖了真实错误，或不同版本执行结果不一致；
-   异常被静默捕获，用户看不到失败原因；
-   翻译文本、技能描述和真实实现不一致；
-   外部资源缺失、路径大小写错误或加载顺序不正确；
-   对本体全局状态或其他扩展造成未预期的副作用。

只检查实际存在的功能。不要为了覆盖清单而臆造仓库中不存在的模块。

### 5.3 为每个模块编写测试场景

每个核心模块至少设计：

-   正常使用场景；
-   边界场景；
-   非法或缺失输入场景；
-   重复触发场景；
-   状态变化后的场景；
-   与相关模块交互的场景；
-   关闭、重新打开或重启后的场景（适用时）。

对于武将技能，应根据机制设计具体局面，而不是只写"测试技能是否正常"。

例如：如果技能依赖目标体力，则覆盖目标体力较高、较低、满体力、濒死或已死亡等适用状态；如果技能依赖手牌，则覆盖无手牌、单张手牌、多种牌型以及没有合法可选牌等场景。实际场景以技能机制为准。

### 5.4 功能正确性的判定标准

-   **通过：** 有代码依据，且适用的测试结果符合预期。
-   **部分通过：** 基本功能可用，但存在已知限制或边界问题。
-   **失败：** 有明确证据表明实际行为不符合预期。
-   **待验证：** 代码不足以确认，必须运行游戏或在指定场景下测试。
-   **设计待确认：**
    现有描述、注释和实现存在冲突，无法安全推断预期行为。

不要把"没有发现问题"直接等同于"已经证明完全正确"。

## 六、问题优先级与修复顺序

采用以下优先级，避免把时间花在低风险细节上。

  ------------------------------------------------------------------------------------------------------
  优先级                  定义                                                   处理方式
  ----------------------- ------------------------------------------------------ -----------------------
  P0                      崩溃、数据损坏、关键功能完全失效、明显安全问题         优先定位并修复

  P1                      核心功能逻辑错误、技能严重误用、主要界面无法正常使用   优先修复

  P2                      特定条件下失效、AI                                     按模块批次修复
                          选择不合理、文字可读性明显不足、模块交互异常           

  P3                      轻微视觉问题、低风险重构、非关键体验优化               核心问题解决后处理
  ------------------------------------------------------------------------------------------------------

每个问题必须有证据。不要仅凭个人偏好把某项实现判定为 bug。

## 七、实际执行流程

### 阶段 1：仓库扫描与基线记录

-   检查 Git 状态和项目结构。
-   读取说明文档、入口文件、技能代码和 UI 样式。
-   生成模块清单、武将技能清单和初步风险列表。
-   记录现有测试命令、运行方式及当前已知问题。
-   不进行大规模修改。

### 阶段 2：静态审查与问题定位

-   扫描 UI 样式中的光晕、模糊、描边、全局选择器和对比度风险。
-   建立武将技能与 AI 配置对应表，逐个审查关键逻辑。
-   梳理各模块的入口、数据流、状态变化和依赖关系。
-   检查语法、导入路径、未定义变量、明显的条件错误和异常处理。
-   为问题记录证据、优先级和验证方法。

### 阶段 3：制定修复清单

先在 `CODEX_AUDIT_REPORT.md` 中记录：

-   发现了什么问题；
-   为什么认为它是问题；
-   影响哪些模块和场景；
-   推荐如何修复；
-   修复可能影响什么；
-   如何确认修复成功；
-   哪些问题需要用户提供设计决定或实机验证。

对存在设计歧义、可能改变玩法或影响平衡的项目，不得擅自进行大幅改动。

### 阶段 4：分批实施修复

建议按以下顺序：

1.  P0/P1 的崩溃、功能失效和逻辑错误；
2.  影响主要使用体验的 UI 可读性问题；
3.  有明确证据支持的技能 AI 错误；
4.  有明确预期的模块功能缺陷；
5.  低风险视觉一致性和维护性优化。

每批修改应尽量聚焦单一问题或相互关联的问题。修改前后检查 Git
diff，不要把无关格式化、大规模重命名或整文件重写混入修复。

### 阶段 5：验证和回归检查

每批修改后：

-   运行项目已有的语法检查、测试、格式检查或构建命令（如果存在）；
-   检查修改文件的差异，确认没有误删功能；
-   对比修改前后的关键逻辑；
-   对技能逻辑使用针对性场景验证；
-   对 UI 检查布局、文字清晰度、点击和状态变化；
-   检查相关模块是否受到副作用影响。

如果当前环境不能运行无名杀，完成可行的静态检查，并明确列出未完成的实机测试。不要伪造测试结果。

### 阶段 6：交付报告

更新 `CODEX_AUDIT_REPORT.md`，总结：

1.  扫描过的模块和技能范围；
2.  已发现的问题及其证据；
3.  已修复的问题和修改文件；
4.  每项修复对应的验证结果；
5.  尚未修复的问题及原因；
6.  需要用户在无名杀内验证的项目；
7.  可能影响兼容性或游戏平衡的改动；
8.  建议的后续优化顺序。

## 八、工程约束与 Codex 行为要求

执行时必须遵守：

-   先阅读代码和项目文档，再做修改。
-   以仓库当前真实实现为准，不假定目录、API、版本和模块名称。
-   优先沿用项目已有的实现方式和兼容策略。
-   对不确定的引擎 API，先检查项目内类型声明、已有用法或可靠的版本资料。
-   不得为了让检查结果"看起来完整"而给每个技能机械添加 AI 字段。
-   不得把个人审美偏好直接当作功能 bug；UI
    改动应以可读性、统一性和实际效果为依据。
-   不得擅自改变技能描述、技能机制、数值和触发条件。
-   不得删除现有功能、素材、配置或兼容代码，除非有证据且改动必要。
-   不得将用户已有的未提交修改覆盖、重置或丢弃。
-   不要把密钥、令牌、个人路径或其他敏感内容写入审查报告。
-   如果没有测试环境，不得声称已通过实机测试。
-   对无法确定的设计意图，应记录问题和候选方案，而不是猜测后直接重写。
-   修改应可审查、可回滚，并尽量保持单个提交或单个批次的改动范围清晰。

## 十、给 Codex 的执行指令

请以当前打开的「池子魔将」仓库为工作目录，严格按照本方案执行。

先完成仓库盘点和代码审查，再根据证据制定修复清单，并按优先级分批实施。不要一开始就大规模重构。对可以明确判断且风险较低的问题，直接修复并验证；对可能改变技能机制、游戏平衡或存在设计歧义的问题，先在审查报告中解释原因和候选方案，不要擅自决定。
