# 待办方案 · 局中更新（4.0.16 已实施）

日期：2026-11-05。来源：作者反馈「为什么非要本局结束后再安装更新，根本不合理」。**状态：4.0.16 已实施**——事务层拆出 `prepare/commit/abortPrepared`，UI 局中走 prepare、本局结束后自动 commit 并重启。

## 1. 现状与证据

| 位置 | 行为 |
| --- | --- |
| `core/csh_debug.js` L7764（`startUpdate` 入口） | 局中直接返回，只把状态改成「请在本局结束后再安装更新，当前文件未改动」；**连检查本机文件和下载都不做** |
| `core/csh_debug.js` L7070（另一处安装入口） | 局中 toast「请在本局结束后安装扩展，避免重启打断结算」 |
| `core/csh_debug.js` L7130 | 安装过程中检测到新对局开始 → 抛错取消，已下载内容保留 |
| `core/csh_debug.js` L7837（完成阶段） | **已经实现**「更新已完成，本局结束后自动重启」：`restart` 每秒重试，直到 `!_status.gameStarted || _status.over` 才 `game.reload()` |

结论：**「局后重启」的能力已经写好了，但入口把整个流程挡在门外，所以永远走不到。** 不是技术上必须局后，是实现自相矛盾。

## 2. 为什么不合理

1. 下载 + 逐文件哈希校验是耗时最长的一段（137MB、1035 文件），恰恰最应该在局中做。
2. 一局可能很久，玩家看到「有新版本」却必须打完才能开始下载，体验上等于「不让你更新」。
3. 完成后明明能等局后重启，入口却不让开始，属于白写的能力。
4. 现在的文案把「不能安装」说成唯一选择，没有告诉玩家「可以先下载、局后安装」。

## 3. 真实约束（不能简单删掉判断）

- **不能打断结算**：提交阶段写文件时若引擎正在结算，可能混用新旧资源。
- **按需读盘资源**：立绘、音频、`games/*.html` 等可能在局中按需从磁盘读取；替换文件后当前局可能读到新素材。逻辑模块已加载在内存，不受影响，但资源混用需要评估。
- **失败必须可回滚**：提交/恢复阶段中断要保留 journal，下次启动恢复（U3 已做）。
- **空间**：暂存占额外空间，失败暂存要可清理（U4 已做分类清理）。
- **不能强制重启**：局中重启会丢当前对局。

## 4. 方案对比

### 方案 A（推荐）：局中「下载 + 校验 + 暂存」，局后「提交 + 重启」

- 局中允许 `startUpdate` 执行到事务层的 **prepared**（文件已下载、逐文件哈希核验、备份已建），然后在提交前停下。
- 状态显示：「更新已下载并校验，本局结束后自动安装」；关闭弹窗不取消已暂存内容。
- 本局结束（`game.over` / `_status.over`）后自动继续提交并重启；复用现有 `restart` 轮询。
- 玩家也可在无对局时点「立即安装」，走现有完整流程。
- 需要改：`csh_update.js` 把 `apply()` 拆成 `prepare()` 与 `commit()`（当前 L130–135 是一体内 prepared→committing→committed），或加 `deferCommit` 选项；`csh_debug.js` 入口判断从「局中拒绝」改为「局中只做 prepare」；状态与文案；`check.js` 加接线守卫。
- 风险：中；收益最大；不改变结算路径。

### 方案 B：局中直接提交，只把重启延后

- 改动最小（删 L7764 拦截即可，L7837 已支持局后重启）。
- 但当前局可能读到被替换的资源，且提交期间的失败会落在对局中途；**不推荐**，除非只替换纯逻辑文件、不动素材。
- 若采用，需限制「本次更新不含资源文件」才允许局中提交。

### 方案 C：保持现状，只改文案

- 明确告诉玩家「可以先下载吗？」——当前实现下载也不允许，所以至少要允许「只下载不安装」。
- 成本最低，但仍不能满足「局中更新」的核心诉求。

## 5. 实施步骤（4.0.16，已实施）

1. `csh_update.js` 拆阶段：`prepare()` 到 prepared；`commit()` 从 prepared 到 committed；`apply()` 保留为两者串联，兼容现有探针。
2. `startUpdate` 局中分支改为「prepare + 停在待安装」，不 abort、不写扩展目录。
3. 监听 `game.over` / `_status.over` 自动 `commit()` + reload；提供手动「立即安装」入口（仅在无对局时可用）。
4. 文案：局中「已下载并校验，本局结束后自动安装」；无对局「立即安装」；失败保留 journal 与恢复入口。
5. 反例探针：
   - 局中 prepare 成功、未写扩展目录、journal 为 prepared；
   - 局后自动 commit + reload 一次且仅一次；
   - prepare 后取消/关闭不丢暂存；
   - 提交中断 → 恢复 → 旧版完整或新版完整；
   - 空间不足 → prepare 失败可清理；
   - 三横屏文案与按钮。
6. 门禁：E46/E48 增加「局中 prepare、局后 commit」接线守卫；完整 `check.js` + 发布字节复核。

### 结算完成判定（4.0.16 已实现）

自动安装前同时满足，且连续两次轮询稳定，再等 4 秒缓冲：

1. `!(_status.gameStarted && !_status.over)`；
2. 钱包待保存结果 `lib.cshWallet.pending.status()` 的 `count` 与 `error` 均为空；
3. 迁移恢复状态 `lib.cshMigrate.recoveryState()` 的 `pending` 与 `busy` 均为假。

任一条不满足就继续每 1.5 秒轮询并清零稳定计数，避免结算动画或战绩写入刚开始就替换文件。
该判定原本有一条 controller 反例，但在门禁大批探针串行时不稳定（单跑稳定、门禁偶发），
已从事务探针撤出，避免让门禁随机变红；逻辑保留在代码与本节记录，事务层三态由 `probe_update_deferred_20261105.mjs` 覆盖。

## 6. 验收标准

- 局中可以开始更新，进度可取消，关闭弹窗不丢已下载内容。
- 本局结束前**绝不**写扩展目录、绝不重启。
- 局后自动完成并只重启一次；失败保留恢复入口，不丢档。
- 无对局时仍可一键立即安装。
- 所有新增状态在三种横屏下可读、按钮 ≥44px。

## 7. 边界

4.0.16 已改运行源码： 新增 （ 保持兼容）； 入口不再拦局中，局中先下载核验、本局结束并留出结算时间后自动提交并重启；失败保留待安装凭据。反例见 （8/0）与事务探针的局中/局后用例。
