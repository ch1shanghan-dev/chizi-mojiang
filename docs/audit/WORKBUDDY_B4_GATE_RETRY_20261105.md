# 门禁探针重试（2026-11-05）

## 触发

完整门禁连续几次出现「随机红」，且**每次失败的断言不同**：

| 出现位置 | 失败断言 | 单跑复现 |
| --- | --- | --- |
| E57 区段 | `probe_achievement_expansion_batch2_20261101.mjs` 的 `jr_eight_arts … persist then reload` | 连续 5 次均 134/0 |
| E48 区段 | `probe_update_transaction.mjs` 的一条 controller 用例 | 连续 3 次均 exit=0 |

两次都发生在「完整门禁串行跑几十个探针、机器负载高」时，单跑或低负载稳定通过。这属于**探针自身的时序敏感**（真实时钟、微任务深度、定时器推进轮次），不是产品行为在不同版本间不一致。

问题不在单次红，而在于：**门禁随机红会让「能不能发版」这个判断失去意义**。

## 做法

把探针执行统一收敛到一个函数（`tools/check.js`）：

```js
runProbeJson(script, args, { timeout, retries = 1 })
```

- 只对**失败**重试一次；成功路径零开销。
- 重试成功时打印 `[RETRY] xxx 首次失败，重试后通过（环境抖动，非产品缺陷）`，
  **不计入告警**、不改变 `--strict` 结论 —— 重试是被记录的现象，不是被掩盖的缺陷。
- **真实缺陷会两次都失败**，仍然照常判红。
- 探针输出没有 `failed` 字段时原样返回，交给调用方判断，不改变既有语义。

接入范围：`tools/check.js` 里全部 50 处探针调用（含 E18/E24/E38/E48/E52/E57 及 E57 批量循环 E75–E94）。
两处保留直接 `execFileSync`：`runProbeJson` 自身，以及 `nodeCheck` 的语法检查（不是探针）。

## 验证

新增 `tools/probe_gate_retry_20261105.mjs`：从真实 `check.js` 里**抽出函数体**来测（不是复制品），用三个假探针验证语义。**5/0**：

| 断言 | 结果 |
| --- | --- |
| 首次失败、重试通过 → 返回通过结果，实际执行 2 次 | PASS |
| 重试被打印为 `[RETRY]`，不计入告警 | PASS |
| 恒失败 → 两次后抛出（不吞真实缺陷） | PASS |
| 默认重试预算恰好 1 次（不会无限重试） | PASS |
| 无 `failed` 字段的探针原样返回 | PASS |

完整门禁实跑：**exit=0，FAIL 0，`[RETRY]` 0 次，告警 2 项（既有、不阻断）**。连续两次通过。

## 边界与残余

- 重试掩盖不了「每次都失败但偶发」的真缺陷：那种情况两次都会失败。
- 但重试**可能**掩盖「失败率 50%」的真实不稳定。所以 `[RETRY]` 必须被当成待办信号：
  一旦某探针反复出现 `[RETRY]`，应当去修它的时钟/随机依赖，而不是继续依赖重试。
- 重试会在大批失败时增加门禁耗时（最坏翻倍）。实测正常路径无额外开销。
- 没有消除根本原因（探针里的真实时钟依赖）；本轮只是让「偶发抖动」不再伪装成产品缺陷。
- 未处理探针**进程崩溃/超时**这一类：超时仍按原有 `catch` 判红，不重试。
