# D2 · 德州真实补码重上桌（设计方案 §3.1 落地）

日期：2026-11-07。版本仍 **4.0.16**，未推送、未合并 main、未发版。未使用子代理。

## 为什么这轮能做

方案 §5 把补码排在「风险最高、放在门禁与反例最完备的时候做」。上一轮全量审计确认
E95A–T 19 项 + 慢速通道 8/0 + 一键套件 15/0 全绿，时机到了。

实施前复核真源码，确认三件事让改动可控：

1. **补码窗口天然存在**：`games/texas/texas.html` 的 `showHandBanner()` 在每手结算后
   给的是「下一手 / 本场结算 / 收工」按钮，**不是自动开下一手**。所以补码能插在
   「一手结算完成、下一手发牌前」，无需改自动流程。
2. **头号红线**：`endSession()` 用 `G.buyIn` 当本金基数
   （`profit = chips - buyIn`）。补码只加 `chips` 而不同步加 `G.buyIn`，
   玩家就能把补码的钱当「盈利」领回钱包 —— 等于刷钱。
3. **德州结算不校验 `buyIn === currentBuyIn`**（该校验只在斗地主 team 分支），
   所以页面累加 `G.buyIn` 后 `settleSession` 会按新基数算净赢，守恒成立。

## 实现

| 文件 | 改动 |
| --- | --- |
| `core/csh_topup.js`（新） | IIFE 纯函数：`quote()` 算时机守卫与额度、`apply()` 做状态转移、`unitOf()` 算 10% 单位、`netOf()` 净赢自检。**不碰 DOM、不落盘、不碰钱包** |
| `core/csh_shell.js` | 新增 `shell-topup` 命令：走与开局带入**同一条** `wallet.spend` 出账路径，`pc()` 读回确认后才 ACK；宿主**独立**校验次数 / 额度 / 单位，不信任子页面金额；读回不一致时回补并如实失败。命令列入 `mutatesSave` 写保护；入场 / 关壳重置每桌次数与原始带入基准 |
| `games/texas/texas.html` | `Bridge.topUp()` 通道；`G` 加 `topUps / topUpTotal / topUpPending`；`topUpQuote()` / `requestTopUp()`；结算横幅加「补码 +N CBY」按钮（输光分支也提供） |
| `tools/probe_texas_topup_20261107.mjs`（新） | **53/0 ×2**，改前基线 2 红 |
| `tools/check.js` | 注册门禁 **E95U**（min 53） |
| `catalog.js` | 按发布字节重生成：**1038 → 1039** |

规则按方案 §3.1：

- **时机**：`G.over` 为 true、`G.ledger.roundId` 与本手匹配（结算已落盘）、本场未结束、
  守恒校验通过、无 pending、次数未达 2 —— 六道守卫全过才提供。
- **额度**：`unit = ceil(原始带入 / 10)`（200 档 = 20），
  `amount = min(ceil((minBuyIn - tableChips)/unit)*unit, walletBalance)`，向下取整到 unit 倍数；
  低于一个 unit 不提供。**原始带入 = `G.buyIn - G.topUpTotal`**，不会因补码累加而漂移。
- **扣款**：宿主 `spend` → `pc()` 读回 → 才 ACK；页面收到 ACK 才 `chips += N; G.buyIn += N`。
  失败 / 回包金额不符 / 迟到回调（会话、手数、结算状态变了）**桌面筹码与本金都不变，可重试**。
- **守恒**：`netOf(chips, buyIn)` 在补码前后恒定；补码不产生也不销毁 CBY。
- **不替玩家消费**：按钮由玩家点击，不自动补码、不自动开下一手；「收工」按钮保留。
- **不改公平性**：只动玩家自己的筹码与本金基数；前注 / 场供 / 已结算手数 /
  已入座者 stake / skill / 发牌一律不动（反例对接线片段有静态断言）。

## 明确未做（不冒充方案完全达成）

1. **跨进程 / 写盘失败的恢复**：`wallet.spend` 用 `scheduleSave()` 异步写盘。
   本轮做到「内存读回确认」，但**持久化写盘失败且进程中断**时，钱包余额可能回滚而
   桌面筹码已上桌。项目已有 `pending` 待保存机制处理结算，补码**尚未接入**。
   方案 §3.1「绝不出现上桌了没扣钱」在**跨进程**这一层还没兑现。这是下一个待办。
2. **离线调试模式不提供补码**（没有宿主钱包，不伪造扣款），按钮明确不显示。
3. **真机 / 实体设备未验**；按钮的横屏布局与触控目标沿用既有横屏规范，未做新截图比对。
4. 补码不产生成就/统计字段，也不改 `BUYIN_TIERS` 四档与退隐联动。
5. 桌面 `池子魔将-4.0.15.zip` 仍未见（上轮审计已记录，未在个人目录擅自重建）。
