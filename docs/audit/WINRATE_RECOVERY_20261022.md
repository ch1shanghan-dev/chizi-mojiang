## 已复现问题

`core/csh_winrate.js` 的 `readData()` 原先直接取得 `lib.config[STAT_KEY]`，再清洗负数、胜负场次、旧 online/offline 格式及十常侍条目。持久恢复凭据尚存时，打开统计、查看阵营或导出仍会改动原配置对象；需要清洗时还会调用 `game.saveConfig`。

`record/recordCamp/recordMe/capture`、导入合并、删除、撤销、重置阵营、清空模式与清空全部也没有接恢复锁。锁在确认框打开之后才出现时，原确认回调仍能写入。因此不能只在面板打开时检查，也不能仅给最终保存套一层检查而保留原对象修改。

证据是实际模块的行为复现。新增 `tools/probe_winrate_recovery.mjs` 用同一组 **127 项断言** 对改前文件得到 **8 PASS / 119 FAIL**，对本批结果得到 **127 PASS / 0 FAIL**。失败数量是多个恢复状态与用户路径的组合，不代表 119 个独立缺陷。

## 修改及可观察行为

- `saveBlocked()` 优先调用钱包共享 `saveGuard.blocked()`；钱包尚未安装时直接读取 `csh_migrate_recovery` 和迁移 `recoveryState().pending/busy`。凭据内容损坏、读取失败、共享守卫抛错时均拒绝写入，不创建新存储键。
- `readData()` 深拷贝已有配置后再执行原清洗。恢复时允许展示、查询和导出清洗后的视图，但不改变原对象、不保存清洗结果。普通状态仍保留原清洗及幂等持久化；交给 `saveConfig` 的清洗结果再次复制，使返回的视图不会因宿主采用保存对象而重新与配置共享引用。
- 角色、阵营、个人角色与个人身份记账在入口和实际保存前检查；`capture()` 入口检查。恢复时跳过统计后，已安装的 `game.over` 包装仍正常调用之前的原生结算，不阻断对局结束。
- 导入合并在修改工作副本前与实际保存前检查。拒绝时导入框显示恢复提示，保持可编辑，不显示导入完成。
- 删除、重置阵营、清空模式在进入操作与异步确认回调中检查；回调重新读取当前历史后再次检查。删除与清空模式固定最初确认的模式，避免等待确认时切换标签后删错桶；重新读取也避免用旧快照覆盖等待期间的新历史。
- 撤销在保存前检查，拒绝时保留尚未过期的撤销快照；清空全部在输入确认后的实际执行点检查。原确认语义、8 秒撤销有效期与导入累加策略保留。
- 新增安全的 `noticeWR()` 提示函数，优先使用既有 UI toast。该文件原来的联机入口与打开失败分支也引用此名称，但未定义；恢复拒绝提示不能再因此抛出未定义异常。

胜负判定、统计公式、历史字段、四模式、模式别名、双将、十常侍合并和身份/个人统计口径保持。未修改迁移恢复自身的严格存储通道。

## 边界

本批保护的是**恢复锁已被本进程观察到时**的普通统计写入。未给 `game.saveConfig` 增加异步成功确认、事务回滚或磁盘失败协议；不能据此声称配置后端任意故障都已解决。统计内存快照也没有新增持久事务格式。
