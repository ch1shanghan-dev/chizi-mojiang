## 1. 方法

```
问题
 ├─ ① 写清事实    什么是不可变的？（引擎给什么 DOM/API、返回什么、契约是什么）
 ├─ ② 写清约束    什么是不可能违反的？（屏幕多大、按钮必须能点、网络会断、玩家会装别的扩展）
 ├─ ③ 排目标      按优先级列结果（先"能不能用"，再"顺不顺手"，最后"好不好看"）
 └─ ④ 只从这里推导 —— 既有实现 / 上次怎么修 / 别人怎么写，只能当参考，不能当依据
      ↓
   方案 A、B、C ……
      ↓ 四条自检
   ① 说得清"为什么必须这样"吗？  ② 换环境还成立吗？
   ③ 边界在哪（输入任意大都不坏）？ ④ 量化验证过了吗？
```

**关键纪律**：推导结论与现有代码冲突时**以推导为准**；
若结论是「方向对但缺一步」，就补那一步，**不整块推翻**（推翻会带来新的未知，违背最小修改）。

## 2. 三条硬约束（怎么推导出来的）

### A. 视口是唯一稳定的参照系

**事实**：扩展能控制的只有自己的 CSS/JS。引擎的 `layout.css`、`body{transform:scale(documentZoom)}`、
十周年UI 之类的覆盖层、玩家装的其它扩展 —— **全都在改 DOM 结构和尺寸，而且随时会变**。
**约束**：屏幕像素是唯一不受这些变化影响的东西。
**目标**：任何元素在任何宿主下都完整可见、可点。
⇒ **所有尺寸必须有「按视口 ÷ 真实缩放算出的绝对上界」，不得继承一个不确定的父容器。**

反例（都真实踩过）：
| 做法 | 为什么错 | 正解 |
|---|---|---|
| `max-height: 70vh` 封对话框 | vh 在 `body{scale}` 里是局部单位（手机 zoom≈0.4 ⇒ 只剩 28% 屏） | `(innerHeight - top - 8) / zoom` 的 px |
| `.buttons{width:100%}` 靠父容器 | 父容器被 UI 插件改宽时按钮墙跟着变宽 ⇒ 右侧几列出屏 | `max-width: 视口宽/缩放`（**只封顶**，别用 `width`） |
| `:has(.card.button)` 认势力面板 | 用 DOM 形态猜语义，命中主菜单 | 按内容判定 + 独立 class 门控 |

### B. 外部输入的数量没有上界

**事实**：势力数量由玩家装的扩展决定（7 个是常态，20+ 个完全可能）；昵称长度、剪贴板内容、
文件清单同理。**约束**：按钮必须 ≥44px 可点、文字必须可读，所以不能"缩小到放得下"。
**目标**：**任意数量**都能全部选到。
⇒ **采用有界布局、滚动、分页或按需加载，保证合法内容可遍历且当前操作可达**，不是缩小、不是裁切、不是只留前 N 个。

### C. 失败必须可见且可恢复

**事实**：网络会超时、远端会 404、磁盘会满、服务端会限流。**约束**：不能靠"重试一次就好"。
**目标**：任何失败都（a）让玩家知道，（b）留下可恢复的路径。
⇒ 禁止两类做法：**静默成功**（丢了文件还提示"更新完成"）、**失败即死路**（只给一句"失败"，没有重试/缓存/清单）。

## 4. 范例：势力面板宽度（本轮的真推导过程）

**① 事实**
- 势力选择走引擎 `chooseButton(["请选择你的势力", [vcard...]])`，DOM = `.dialog > .content-container > .content > .buttons`。
- 引擎 `layout.css:1560` `.buttons { width: 100% }` —— 跟着父容器走。
- `.dialog` 宽度由引擎 `calc(90% - 420px)` 给出，**但 UI 插件会覆盖它**。
- 玩家装的扩展会把 `lib.group` 从 7 个扩到 20+ 个。

**② 约束**
- 屏幕宽度是硬上界，按钮必须 ≥44px 可点（不能缩小）。
- 不能改引擎 CSS、不能假设 UI 插件的行为（G4 零侵入）。

**③ 目标**
- 首要是「任意数量的势力**全部可选到**」，其次「不遮挡」，最后「好看」。

**④ 推导**
> 只要 `.buttons` 的宽度跟着一个不受控的父容器走，**换行就会在错误的宽度上发生**，
> 一旦那个宽度大于屏幕，右侧必然出屏 —— 不管按钮多少个、屏幕多大。
> 所以必须给宽度一个**与父容器无关的绝对上界**。
>
> ★ 但这个上界**只能写成 `max-width`（被动），不能写成 `width: min(100%, N)`（主动）**。
> 这是第二批实机反馈补上的（作者："每次出现这个自适应窗口会这样一下"）：
> 引擎给 `.buttons` 的是 `.content > div:not(.pointerdiv){width:calc(100% - 8px)}`（layout.css:1857）。
> 写成 `width` 会把它**覆盖掉**，等于每次都比原布局宽 8px；再叠加当时给容器加的
> `padding-right:10px`（窄 10px），两个方向一起动 —— 按钮列数就压在临界值上，
> 4 列 / 5 列来回跳。`max-width` 不会：**没超就一个像素都不动**。
> 纵向靠滚动，因为行数变多是不可避免的，不是 bug。

**⑤ 当前验证（2026-10-21）**

`node tools/probe_eg_scroll.mjs` 执行实际content辅助函数和本机引擎layout.css，隔离Chromium **49/0**；同轮备份 **30/19**。
覆盖正常窗口宽度不变、1400px父宽、动态节点/面板复用/后注册势力、样式及important归还，五档scale/zoom下的窗口/控制条矩形、滚动到底后末项指针命中，及真实双轴滚轮。
`probe_egwidth.cjs` / `probe_egnoflash.cjs` 旧脚本仍复制废弃width/padding方案的问题已纠正，现在委托真实源码专项；历史表格不作为当前实测证据。
`node tools/probe_egwidth.cjs 375 667 0.5 24 140` 加三档父宽对照 **56/0**。
详见[专项报告](audit/KAMI_SCROLL_AUDIT_20261021.md)；无名杀完整游戏、安卓触摸与联机待验。
