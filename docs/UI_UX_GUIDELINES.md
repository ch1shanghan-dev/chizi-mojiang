# 池子魔将｜UI/UX 术语词典、设计体系与 Codex 开发规范

> **用途**：作为《池子魔将》无名杀（Noname）扩展的长期 UI/UX 规范与 Codex 开发参考。
>
> **适用范围**：池子世界、妖灵图鉴、羁绊、成就、行囊、德州/博弈结算、扩展设置、武将与技能相关界面，以及后续新模块。
>
> **使用方式**：将本文件放置在项目内 `docs/UI_UX_GUIDELINES.md`（推荐）；再将第 10 节的精简指令合并进项目根目录 `AGENTS.md`。不要覆盖已有 `AGENTS.md`。
>
> **注意**：本文件属于设计与工程约束方案，未自动审计仓库源码；具体组件实现应以仓库、无名杀版本与现有技术栈为准。

## 1. 核心认知：不是所有“弹窗”都是 Modal

日常说的“弹窗”只是模糊称呼。真正开发时要描述：**出现位置、是否阻断背景、与哪个元素关联、承载多少信息、怎样关闭、是否需要常驻**。

例如：

- “点角色头像弹个东西” → 如果有原画、羁绊和多组操作，可能是 **角色详情 Dialog / 独立详情页**，不是小 Tooltip。
- “点设置按钮从右边拉出来” → **Drawer（抽屉）**。
- “鼠标移到技能名上出现一两句话” → **Tooltip（工具提示）**。
- “点技能旁问号出现带按钮的说明” → **Popover（锚定悬浮面板）**。
- “操作成功后短暂提示” → **Toast（轻提示）**。
- “移动端从底部升起的一组选择项” → **Bottom Sheet（底部操作面板）**。

**重要区分**：`Dialog`、`Drawer`、`Sheet` 更偏向界面结构/形态；`Modal` 描述交互是否阻断背景。**Drawer 可以是模态的，Dialog 也可以是非模态的**。不要混淆这些维度。

### 描述 UI 时的六维模板

> **触发**（点哪里）+ **形态**（Dialog/Drawer/Popover 等）+ **位置**（居中/右侧/锚定）+ **内容**（显示什么）+ **行为**（能做什么）+ **关闭**（Esc/遮罩/按钮）

例子：

> 点击妖灵头像，打开**右侧模态 Drawer**，显示半身原画、羁绊档位和互动入口。抽屉内滚动，不影响背景布局；点击关闭按钮或按 Esc 退出。移动端改为全屏详情页。

## 2. UI/UX 术语词典

| 英文术语 | 中文名称 | 典型特点 | 在池子魔将中的应用 | 常见误用 |
|---|---|---|---|---|
| **Modal Dialog** | 模态对话框 | 盖住背景、要求先处理当前任务 | 德州本局结算、重要奖励确认 | 所有内容一律做居中弹窗 |
| **Dialog** | 对话框 | 集中展示一项任务，可模态或非模态 | 角色详情、交易确认 | 把常驻工具区做成对话框 |
| **Alert Dialog** | 警告确认框 | 危险、不可逆操作的明确确认 | 清空存档、覆盖配置 | 普通成功提示也要求确认 |
| **Drawer** | 侧边抽屉 | 从左/右侧进入，容纳较多设置或细节 | 妖灵图鉴、筛选、扩展配置 | 抽屉内容过多却缺乏导航 |
| **Bottom Sheet** | 底部面板 | 从底部升起，适合移动端 | 移动端武将选择、快捷兑换 | 桌面端无差别使用大底部面板 |
| **Popover** | 锚定悬浮面板 | 依附按钮/图标，可包含交互内容 | 羁绊奖励详情、轻量技能操作 | 放进大量复杂表单 |
| **Tooltip** | 工具提示 | 简短说明，一般不需要复杂操作 | 技能关键字、数值解释 | 把需要点击的复杂控件塞进去 |
| **Dropdown Menu** | 下拉菜单 | 命令或选项列表 | 排序、操作选项 | 用下拉菜单展示长篇内容 |
| **Context Menu** | 右键/情境菜单 | 与当前目标关联的操作 | 武将卡片的更多操作 | 仅有鼠标右键入口、移动端无法使用 |
| **Toast / Snackbar** | 轻提示 | 短暂反馈，不阻断流程 | 获得 CBY、保存成功 | 关键信息仅出现一瞬间 |
| **Banner / Inline Alert** | 页面内提示条 | 持续提示风险或状态 | 云端同步失败、存档冲突 | 用自动消失 Toast 显示重大错误 |
| **Sidebar** | 常驻侧栏 | 导航、分类、长期显示 | 池子世界模块导航 | 与临时 Drawer 混为一谈 |
| **Tabs** | 标签页 | 切换同层级内容 | 妖灵：信息/互动/记录 | 层级过深形成多层标签套娃 |
| **Accordion** | 手风琴折叠面板 | 分组展示按需展开 | 帮助、日志、次级规则说明 | 主信息默认全部折叠 |
| **Lightbox** | 大图预览层 | 放大图片并聚焦视觉内容 | 武将/妖灵原画浏览 | 全部信息都叠在原画上 |
| **Carousel** | 轮播区域 | 同类卡片横向切换 | 武将原画集、主题外观 | 关键数据只能轮播才能找到 |
| **Command Palette** | 命令面板 | 搜索并快速执行指令 | 开发模式或高频入口 | 普通玩家被迫记忆命令 |
| **Overlay / Backdrop** | 遮罩层 | 背景暗化、焦点隔离 | 模态 Drawer/Dialog 背景 | 多层遮罩叠加、无法关闭 |
| **Progress Indicator** | 进度指示器 | 显示阶段、当前值与目标值 | 羁绊经验、挑战进程 | 数据超界仍按固定进度画满 |
| **Skeleton** | 骨架屏 | 异步加载的视觉占位 | 云端数据、图鉴资源加载 | 无数据也永久显示骨架屏 |
| **Empty State** | 空状态 | 解释为什么没有内容并给出行动 | 暂无成就、没有交易记录 | 留一片空白或只显示“0” |
| **Stepper / Wizard** | 分步流程 | 按阶段完成多步操作 | 复杂新手引导、初始化配置 | 两步操作也拆成很多页面 |
| **HUD** | 游戏平视信息层 | 战斗时常驻关键提示 | 身份场妖灵状态、战斗加成 | 挡住核心战斗操作 |

### 易混淆术语的判断

- **Tooltip vs Popover**：只有简短解释 → Tooltip；需要按钮、列表、交互 → Popover。
- **Drawer vs Sidebar**：临时滑出的配置/详情 → Drawer；长期导航 → Sidebar。
- **Toast vs Dialog**：操作成功通知 → Toast；必须做决定 → Dialog。
- **Tabs vs Accordion**：同层内容二选一/多选一 → Tabs；同一页面的分组展收 → Accordion。
- **Lightbox vs 详情页**：主要为了看大图 → Lightbox；还有丰富属性、任务与交互 → 详情页/Dialog/Drawer。

## 3. Codex 的组件选型规则

开发者如果只说“弹窗”“搞个面板”“整好看点”，不能直接机械实现。首先分析内容和交互目的。

| 需求条件 | 推荐组件 | 原因 |
|---|---|---|
| 危险/不可逆操作必须确认 | Alert Dialog | 降低误触与误操作 |
| 结算结果需重点展示、下一步行动明确 | Modal Dialog | 焦点集中 |
| 设置多、可分组、需要滚动 | Drawer / Settings Page | 容量更大、结构更清晰 |
| 依托图标的局部互动 | Popover | 不离开原上下文 |
| 简单解释一两句话 | Tooltip | 信息轻量 |
| 成功/普通提示 | Toast | 不打断操作 |
| 失败且需要主动恢复 | Inline Alert / Dialog | 错误不应随时间消失 |
| 多张原画连续浏览 | Lightbox / Gallery | 强化视觉体验 |
| 长期导航和分类 | Sidebar / Tabs | 结构稳定 |
| 手机端选项列表 | Bottom Sheet | 符合触屏操作 |
| 信息非常多、需频繁使用 | 独立页面 | 避免所有模块变成巨型弹窗 |

**默认决策次序**：信息是否必须阻断 → 内容量 → 是否锚定触发元素 → 使用频率 → 屏幕尺寸 → 与现有界面一致性。

### 避免这五种反模式

1. **万能居中框**：任何交互都使用同一套黑色半透明居中 Modal。
2. **标题套娃**：总标题、模块标题、分组标题占据过多有效空间。
3. **视觉堆料**：过度光晕、模糊纹理、金色边框和阴影，反而导致文字难读。
4. **状态不明**：加载、失败、禁用、无数据、处理中没有清晰反馈。
5. **交互缺口**：只有鼠标能操作；Esc 无效；底层仍可滚动；手机上越界。

## 4. 池子魔将专属视觉与交互原则

### 4.1 视觉目标

关键词：**精致、沉浸、统一、清晰、有张力，但不能牺牲可读性**。

- 原画是重要视觉资产。角色展示避免“证件照式”裁切，保留上半身主体、构图张力与必要留白。
- 重要数值大而易读；次要说明采用低一级对比度，不用光晕制造层级。
- 统一按钮样式、圆角、间距、层级、图标笔画、过渡节奏，而不是每个模块各做一套。
- 必须对长中文、数字变化、超额值、极端值设计溢出方案。
- 兼顾 PC 与移动端；不能依赖 Hover 才可读取关键内容。

### 4.2 建议定义的设计 Token（仅为初始建议）

### 4.3 必须检查的交互细节

- 打开与关闭、动画完成前快速重复点击。
- 焦点进入、焦点返回、Esc/关闭按钮、是否允许点遮罩关闭。
- 背景滚动锁定、弹层嵌套、滚动穿透、触屏滑动。
- z-index 和 stacking context，不靠任意堆叠极大数值解决。
- 网络慢/数据为空/失败重试/状态持久化。
- 长文本、超大数字、缩放比例、小分辨率和高 DPI。
- 手柄/键盘场景如项目支持，也要具备合理焦点顺序。

## 5. 现有模块的具体建议

> 以下是结合需求与先前提供的界面截图提出的**设计方向**，不是声称已检查对应源码。

### 5.1 妖灵图鉴与羁绊详情

**推荐形态**：PC 采用宽幅角色详情 Dialog，或右侧 Drawer；移动端优先全屏详情页/Bottom Sheet（按实际内容量选择）。

- 左侧原画占据主要展示面积，但不得导致右侧关键数据被挤压。
- 右侧分区：角色介绍 → 羁绊等级与累计进度 → 可执行互动 → 近期反馈；次要文字收敛到折叠区。
- Tooltip 解释“羁绊等级/经验阈值”；Popover 展示下一档奖励；Toast 展示“互动成功”。
- **严禁显示逻辑冲突的 `182 / 100` 并同时写“距离下一档还差 1818”**，除非清晰标注不同口径。应区分“当前档内进度 / 当前档所需经验”和“总累计羁绊值”。
- 进度条可视比例必须限制在 `0%–100%`，实际数值溢出不能被悄悄抹掉；升档后正确换算至新档位。
- 如果顶部出现多个关闭按钮或相互覆盖，应统一到一个明确的主关闭入口。

### 5.2 德州结算

**推荐形态**：紧凑、信息层级清楚的 Modal Dialog。

- 主区先展示“本手净变化”“当前余额”“下一步”。
- 次区按玩家展示投入、返还、收益；避免六行重复为零的数据压制关键结果。
- 账本必须区分：投入、奖池分配、返还、场供、净变化；不能把平局返还误判成盈利。
- 结算正确性优先于界面重绘，UI 重构不准改变经济逻辑。
- 当全部玩家为 0 收益时，也需要清晰解释当前是平局、返还，还是异常结算。

### 5.3 池子成就

**推荐形态**：独立成就页 + 分类 Tabs/Sidebar + 卡片网格 + 详情 Popover 或 Drawer。

- 先展示达成进度、可领取奖励与最近解锁；不要让大标题占据大部分页面。
- 未完成成就需要可理解的达成条件；已完成可领取状态必须明显。
- 空状态应区分“没有数据”“尚未达成”“功能不可用”。

### 5.4 池子世界与扩展设置

**推荐形态**：长期导航使用 Sidebar；临时设置使用 Drawer；重要二次确认使用 Alert Dialog。

- 设置项按功能分组，提供必要但不过度的解释。
- 例如“妖灵乱入”作为身份场专属功能，应展示生效范围、开启状态及规则摘要。
- 无法兼容的模式下明确禁用并说明原因，而不是隐藏报错。

### 5.5 行囊与物品打包

**推荐形态**：主列表 + 批量操作工具栏；高级筛选 Drawer；轻量结果 Toast。

- 高频操作应少点几次即可完成。
- 无需长篇固定说明，复杂规则放入可展开帮助区。
- 危险的清空/批量删除操作要求 Alert Dialog 确认。

### 5.6 武将技能与 AI 信息

**推荐形态**：技能关键字 Tooltip、详细机制 Popover、完整武将详情页。

- 不要把长技能解释全部塞进悬浮 Tooltip。
- 移动端确保关键说明可点击，不依赖鼠标悬停。
- 游戏内使用的图标和按钮应遵循统一视觉语言。资源版权与使用授权需核查，避免直接使用未授权图片。

## 6. 逐步建立可复用 UI 组件体系

推荐目标组件目录（**示意结构**，应先适配现有项目，不要求强制重构成 React/Vue）：

```text
extension-root/
├── AGENTS.md                       # Codex 项目约束（合并第10节）
├── docs/
│   └── UI_UX_GUIDELINES.md         # 本规范
├── ui/                              # 实际位置按项目结构调整
│   ├── tokens/                      # 颜色、尺寸、间距、层级、动效
│   ├── primitives/                  # Button, Card, Icon, Progress 等
│   ├── overlays/                    # Dialog, Drawer, Popover, Toast 等
│   ├── gameplay/                    # CharacterPanel, BondProgress 等
│   └── utils/                       # 焦点、层级、滚动锁、尺寸适配
└── ...
```

### 第一批优先标准化的组件

| 优先级 | 组件 | 最重要的统一规则 |
|---|---|---|
| P0 | Dialog / Drawer | 焦点、关闭、遮罩、滚动锁、层级 |
| P0 | Button / IconButton | 状态、尺寸、点击区域、禁用反馈 |
| P0 | Toast / Inline Alert | 成功失败信息、持续时间、错误可恢复性 |
| P0 | Progress / Stat | 极端值、累计值、档内值口径一致 |
| P1 | Card / Section / Tabs | 信息密度与视觉层级 |
| P1 | Popover / Tooltip | 定位、溢出、鼠标与触屏兼容 |
| P1 | CharacterDetail / ArtworkViewer | 原画安全裁切、信息展示 |
| P2 | EmptyState / Skeleton | 加载、无数据、错误分支 |
| P2 | Search / Filter / Command Palette | 大规模信息检索 |

**工程原则**：优先识别并复用已有实现。除非证据充分，不要凭空引入新框架、UI 库或批量替换组件。

## 7. Codex UI 开发工作流

每次接到 UI 需求，按以下次序执行：

1. **理解意图**：把口语需求转成组件类别、交互目标、用户路径、信息层级。
2. **检查代码**：定位入口、状态来源、样式、现有组件、兼容逻辑。
3. **选择形态**：说明选择 Dialog/Drawer/Popover 等的理由和替代方案；在需求清晰时自主决定，不为了澄清而阻塞进度。
4. **最小侵入**：先避免改动存档、经济、战斗判定等非 UI 逻辑；需要修改时明示范围。
5. **复用组件**：避免每个模块重复编写遮罩、定位和关闭逻辑。
6. **实现完整状态**：默认、Hover/Focus、Active、Disabled、Loading、Empty、Success、Error。
7. **验证行为**：PC + 移动端视口，关键操作路径，快捷键、焦点、滚动锁和边界数据。
8. **对比改造前后**：审查信息密度、可读性和实际功能是否退化。
9. **汇报改动**：说明改了什么、为什么、测试了什么、剩余风险是什么。

### 推荐输出格式

```text
【需求理解】
- 用户原话：……
- 实际交互目标：……
- 推荐组件：Drawer（而非通用 Modal）
- 桌面端 / 移动端差异：……

【代码现状】
- 入口与相关文件：……
- 复用组件：……
- 风险：……

【实施】
- 修改范围：……
- 不修改范围：存档/游戏胜负/经济结算（除非明确授权）

【验证】
- 打开与关闭、Esc、焦点、滚动锁：……
- 长文本、数字溢出、窄屏：……
- 回归测试：……
```

## 8. UI 质量验收清单

### 组件语义与信息层级

- [ ] 组件类型符合实际用途，没有将所有交互都做成居中 Modal。
- [ ] 页面视觉重心清晰，主要信息能够一眼看到。
- [ ] 不存在标题过多、辅助说明太长、信息密度过低的问题。
- [ ] 文案与数字口径一致，无溢出、截断和误导性进度条。

### 交互与可访问性

- [ ] 支持明确关闭路径，Esc/遮罩行为符合预期。
- [ ] 焦点合理转移并在关闭后返回，必要时阻止焦点进入背景。
- [ ] 键盘、鼠标和触控可完成关键操作。
- [ ] 反馈覆盖成功、失败、加载、空状态。
- [ ] 模态场景没有背景滚动穿透或多个无效遮罩。

### 视觉与响应式

- [ ] 原画显示合适、未关键部位裁切、不被文字过度遮挡。
- [ ] 字体清晰，没有过度光晕导致阅读困难。
- [ ] 屏幕缩放、分辨率变化、窄屏和长文本正常。
- [ ] 图标、间距、边框、按钮、色彩与现有设计体系一致。
- [ ] 动效不干扰操作，并考虑减少动态效果偏好。

### 工程质量

- [ ] 未破坏原有存档、统计、货币、成就、技能和回合逻辑。
- [ ] 无明显控制台错误、监听器泄漏、重复挂载和事件残留。
- [ ] 同一 UI 能通过实际启动和交互验证，而不仅是静态代码检查。
- [ ] 已记录测试步骤、结果与未解决问题。

## 9. 给 Codex 的典型需求表达方式

### 低质量描述

> 把这个弹窗弄漂亮点，按钮别那么 low。

### 改进后的专业描述

> 请检查当前界面的使用场景，先判断它应当使用 Dialog、Drawer、Popover 或独立页面。目标是提高信息可读性、空间利用率与视觉一致性。优先复用项目已有组件与样式 Token，保留原有业务行为。完成后测试关闭方式、移动端适配与异常状态。

### 针对羁绊界面

> 角色原画为视觉主体，羁绊卡片清晰展示**总累计值、当前档位进度和下一档门槛**。若数值超出阈值，应核对升级换算逻辑，不得只在 CSS 中掩盖。羁绊解释采用 Tooltip，档位奖励详情采用 Popover 或侧边 Drawer。修正后验证多次连续升级和最大档位。

### 针对德州结算

> 将结算设计为紧凑 Modal Dialog，突出本手净变化、余额与下一手操作。玩家明细可以折叠或降低视觉权重。先验证账本口径与场供逻辑，不能通过前端展示掩饰算账错误；确认余额守恒后再优化 UI。

### 针对池子成就

> 请重构成以成就卡片和可领取奖励为中心的浏览界面，顶部只保留必要统计，分类使用 Tabs 或 Sidebar，详情采用 Drawer/Popover。确保每个成就的触发条件、达成状态、领取动作真实可用，避免只做视觉空壳。

## 12. 实施优先级建议

| 阶段 | 工作重点 | 完成标志 |
|---|---|---|
| **P0：规范与安全回归** | 术语统一、弹层关闭与层级、业务数据边界 | 不破坏现有功能，羁绊与结算展示无明显矛盾 |
| **P1：通用组件体系** | Dialog、Drawer、Button、Popover、Toast、Progress | 同类组件具有一致的行为与视觉 |
| **P2：重点页面改造** | 成就、妖灵详情、池子世界、德州结算、行囊 | 信息密度合理、主要操作清楚 |
| **P3：视觉精修** | 图标、材质、动效、原画布局、响应式 | 多模块风格统一且操作流畅 |

**最终原则**：专业术语是工具，不是目的。真正的目标是让 Codex 准确理解需求，用合理的界面结构实现更好用、更好看、更稳定的池子魔将。
