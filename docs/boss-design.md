**★ 键系统一铁律（v3 · 4.0.6 妖灵 BUG 根因）**：`allBossIds()` 返回【boss ID】（csh_boss\_*），与
  
entries/cfg/names **同键系**——禁止任何手工 `slice(4)/slice(9)` 键转换（用 `bossIdOf()/origIdOf()`）。
  
违反 = 4 人局 + 魔王摸 8 丢失。执行级断言 E1/E2/E4 守护。

**★ 原生注册铁律（v4 · 最重要）**：魔王角色必须走 **`game.import("character", factory)`**——
  
引擎启动时（`noname/init/index.js:465`）`loadCharacter()` 与扩展角色**同一条原生流程**（lib.character /
  
skilllist / forbidai(isBoss 自动) / characterPack / translate 全套处理）。**禁止手工写 lib.character /
  
mode_boss 包**（v3 手工塞 = 绕过引擎 → 条目形态不一致 → optionsMenu.js:203 等 [N] 直读 TypeError；
  
补丁越修越臃肿）。配套两条硬约束：
  
① 包必须**先登记启用**（`lib.config.characters.add("池子魔将_boss")`，在 game.import 之前）——否则
  
`loadCharacter` 因包未启用直接 break 跳过（`loading.js:110`），魔王全不加载；
  
② 条目为**对象形态**（与 character/index.js 原生条目同格式），由 `buildBossEntries()` 的
  
`ensureIndex()` 补齐数组索引 `[0]/[1]/[2]/[3]/[5]` 双通道（引擎多处 [N] 直读）。断言 E5/E7/E8 守护。

**★ 立绘守护铁律（v3 · 实机黑影根因）**：polyfill `setBackground`（`polyfill.js:117`）对
  
**`lib.characterPack["mode_"+mode]` 内的条目**强制走模式立绘目录（`image/mode/boss/character/*.jpg`）→
  
黑影。因此 **mode_boss 包永远不写我方条目**；我方条目由原生注册进 lib.character，立绘路径（extension/…）
  
正常生效。断言 E5 守护（bossmode 零手工写）。

**★ 变量纪律铁律（v4 · 实机 556 行报错根因）**：`filter(event, player)` 的参数只有 event/player——
  
**trigger 仅在 content 内由引擎注入**；filter 内引用 trigger = ReferenceError。断言 E9 守护。
  
另：`_status.turnCount / _status.round` 引擎均不存在（回合计数用 roundStart 子技自增 storage）；
  
子技（`_die/_round`）必须 `silent: true`（防无译名抢跑）。

**★ 包级隐藏（v4 · 作者定案"武将设置页不可见"）**：武将设置页包节点枚举 = 静态包列表 +
  
**lib.characterPack 全键兜底补建**（`characterPackMenu.js:424-430`）——单靠条目级 `isUnseen`
  
只隐藏条目、节点仍在。两层做法：① 魔王条目带 `isUnseen: true`（武将页条目过滤 `characterPackMenu.js:144`

- 选将池 `ui/create/index.js:1201`，对 isBoss 本已不可选，纯观感）；② `main/content.js` 在 content 时点
    
  （引擎 loadCharacter 已跑完）调用 `character/boss.js` 导出的 `cshBossPackHide()` —— **`delete lib.characterPack["池子魔将_boss"]`**
    
  （守卫：仅当魔王确实已进 lib.character 才移除）。`get.character()` 先查 lib.character → 一切读取不受影响；
    
  换模式/重载后模块重新 add + game.import，循环成立。断言 E10 守护。

## 2. 注入机制（v4 现状 · 两条路径）

- 启动链：扩展导入（`init/index.js:267-277`）→ 模式 import（298-311）→ `loadMode`（462）→
    
  **`loadCharacter` 全量（465，game.import 的包在此落地）** → **扩展 `content`（521-522 · 注入黄金位）**
    
  → `mode.start()`（528+）。单机换模式/开局 = 整页重载 → lib.* 全量重建，无跨局残留。
- **`character/boss.js`（原生注册）**：模块加载时 `lib.config.characters.add(NAME)` → `game.import("character", …)`
    
  工厂从**扩展包原始数据**（`character/index.js` 导出，不依赖 lib.character 时序）构造 93 + 6 条目 →
    
  引擎 loadCharacter 全量处理。译名带档位前缀（究·/霸·/彩·，精英不加）。
- **`main/bossmode.js`（模式配置，判 `mode==="boss"`）**：`buildBossConfig()` 纯静态 → 逐键写
    
  `lib.boss[bid] = {chongzheng, _csh_moxi, _csh_x, minion?, gameDraw}`（global 等他方键保留）+
    
  `lib.storage.current` 首进焦点（空值时落我方首位）。`lib.boss` 在 mode.start 末尾被 delete（瞬态），
    
  每次进模式由 content 重新注入。
- **零污染**：魔王不进 character/index.js 名册（不进 AI 世界）；选将排除 isBoss
    
  （`ui/create/index.js:1190`）；随机获技跳过（`get/index.js:4196/4243` isBoss→continue）；
    
  其它模式注入零执行；盗道（塞拉斯）整体排除 `csh_boss_*`（v4）。

**已复核但判定「非缺陷」的疑点（留档，避免后人重复怀疑）**：

- `csh_boss_watch` 的 `trigger: {global: "dieAfter"}`：**有效**。`dieAfter` 不是"元素方法"而是
  **引擎对每个事件自动追加的 After 阶段**（`gameEvent.js:249 await trigger("After", 4)`）——
  魔王死一次即可靠触发，无需担心 boss 模式未定义 `element.player.dieAfter`。
- 妖灵【矜持】`globalTo`：**有效**。`get.distance` 的 `checkMod(from, to, n, "globalTo", **to**)`
  末位参数是 `to`，遍历 **to 自身技能 + lib.skill.global** ⇒ 距离计算里 `to` 就是妖灵本人，
  直接挂技能即可（这正是 `globalTo` 与 `maxHandcard` 需要 global 的差别所在）。
- 魔王死亡不会因"重整"重复计数：重整的 `dieAfter` 只对**非魔王**清零 `boss_chongzheng`
  （`mode/boss.js:460`），魔王一死即 `game.checkResult()` → 一局只可能"被讨伐"一次。
- 讨伐录 `Data.fresh` 无竞态：`renderAll()` 每次入口都重算 `seen/fresh`（数据到达后再渲染）。
- 三张页面的 `<style>` 逐条规则体**全部成对闭合**（机械校验 depth=0 / 括号差=0）——
  2026-10-14 修过的「CSS 未闭合吞规则」没有复发。
- `player:` / `source:` / `target:` / `global:` 四类触发的**事件-角色组合**全部合法
  （逐条对照引擎事件字段清单）。

**已知设计现象（非 BUG · 供作者决策）**：

1. **妖灵会随【重整】复活**（`mode/boss.js` 重整对"所有非魔王"生效 = 挑战者与妖灵都会复活）。
   因此同一局内同一只妖灵可被反复击破 → **每次都发 15000 CBY + 25 功勋 + 热度**。
   这与作者定案"按被讨伐次数给、重复挑战也给"的字面一致，但构成局内刷钱口（究极档重整 6，
   妖灵 4 血）。**单点旋钮 `MINION_CBY`**；若要在"局内去重"，最小改动是给
   `recordMinion` 加 `sameGame` 去重（按 `_status` 局标识）。
2. **应战模式（玩家即魔王）下妖灵阵亡仍照发奖励**：`csh_boss_watch` 的妖灵分支不判阵营，
   钱包是玩家的 ⇒ 玩家当魔王时自己的妖灵被杀也会入账 15000。若需收口，在妖灵分支加
   `game.me !== game.boss` 即可。
3. **速通 `best` 记录的是"魔王首次阵亡的轮数"**，而配对是随机妖灵 + 档位血量，
   同一魔王的成绩受随机搭配影响——榜单对比时需注意口径。

### 20.4 妖灵收益同局去重（"一局只能获得一次讨伐收益"）

**背景**：v6 把精英档重整由 0 调到 2 ⇒ 妖灵会随重整复活。若不设防，同一局反复击破同一只即可反复领 15000 CBY。

**实现**（`core/csh_bossrecord.js`）：

```js
let guardOwner = null, guardSet = null;
function guardPass(minionId, owner) {
	if (!owner) return true;                       /* 未传 owner（单测/调试）→ 不去重 */
	if (guardOwner !== owner) { guardOwner = owner; guardSet = {}; }
	if (guardSet[minionId]) return false;
	guardSet[minionId] = 1;
	return true;
}
```


**为什么用「本局魔王对象」当分期钥匙**：
- `game.boss` 每局都是**新对象**（`game.players` 逐局重建）⇒ `owner !== lastOwner` 天然判定"换局"；
- **不需要新增存储、不需要定界事件**（模式重进 / 再来一局都不会误删或残留）；
- 页面重载会丢，但重载本就中断对局——语义无损。
- **反面方案**（已否决）：给 `cshBossModeInstall` 挂 `newRun()` 重置模块级 Set —— content 是**每页一次**，同页多局时会**永久锁死**后续所有收益。

粒度 = **按妖灵 id**：同一只第二次击破不再结算，**同局内的其它妖灵照常结算**。
`skills/boss.js` 的 `csh_boss_watch` 透传 `{ owner: game.boss }`。门禁 **E13** 扩为四断言（★ 2026-10-16 三轮/四轮修正后：MINION_CBY=800 / MINION_CBY_ASBOSS=800 / recordMinion(minionId, opts) / watch asBoss 传参）。

### 21.3 池子币账本（做账）

**设计要点**：
- **单一写入点**：全项目资金流动只走 `addPC` / `spendPC` ⇒ 在出口记账，账本**天然全量**，
  不必在 20 多个业务点各写一次（这正是"不可避免的漏记"的根治办法）。
- **与 `wallet.chain` 分工**：哈希链是防篡改校验（`{s,d,b,h}`，人看不懂），账本是给人看的
  `{t, d, r, c, b}`——两者并存、互不替代。
- **分类推导**：`catOf(reason)` 按前缀归 16 类（讨伐首杀 / 每日首战 / 妖灵讨伐 / 签到 /
  破产救济 / 每日任务 / 成就奖励 / 股市买入 / 股市卖出 / 股市分红 / 门票 / 牌桌带入 /
  牌桌结算 / 兑换码 / 亲征 / 其它）——**业务侧一行都不用改**。
- **容量**：滚动 400 笔（localStorage 一本小账）。
- **通道**：`shell-ledger` **单列一条命令**，不并进 `walletSnapshot`（后者是每局开局的轻快照，
  账本 20~30KB 不能拖它）。

**UI（生涯大厅「账本」页 · GitHub 贡献图范式）**：四个总额（累计入账 / 累计支出 / 净额 / 笔数）
→ **近 42 日收支热力格**（7 行 = 星期、列 = 周，格子按当日流量分 4 档、按净额取色，hover 有明细）
→ 分类汇总（双向条 + 金额 + 笔数）→ 逐笔流水（时间 / 分类徽章 / 说明 / ±金额 / 结余）
→ 分类过滤 chips。**总览页的池子币大数字即入口**（作者圈出的那个位置）。

### 23.4 黑心 BUG（根因 + 修法）

爱心原实现是 `svg.innerHTML = '<defs><linearGradient id="hgXXXX">…</defs><path fill="url(#hgXXXX)">'`

光晕改用 CSS `drop-shadow`。即使光晕失效，爱心本身仍是粉的 —— **失败模式从"变黑"降级为"少一层光"**。

### 24.1 ★「她疏远了你」第一天就弹 —— 根因与修法

**根因**：`moodOf()` 的判据是 `(Date.now() - e.last) / 86400000 > 14`。

1. `e.last` 是**毫秒时间戳**，写入时取 `Date.now()`；
2. 判据**没有任何合法性检查**（不看 `last` 是否落在合理区间、是否为 0、是否在未来）；
3. 于是它**完全受系统时钟摆布** —— 作者实机时机器时间被前后调过（本项目前几轮已多次出现
   "时间戳脏数据"），`last` 直接落到十几年以外 ⇒ **一个刚实装的存档被判"14 天没来"**，
   当场弹出「她疏远了你」。**这与"实装第几天"完全无关**，是判据选错了量纲。

**修法（换量纲，不换语义）**：疏远**只看日键 `saw`（`YYYY-MM-DD`）**，彻底不看毫秒。

```js
function dayGap(a, b) {          /* 日键差（b - a，单位天）；任一段非法返回 null */
  var pa = String(a || "").split("-"), pb = String(b || "").split("-");
  if (pa.length !== 3 || pb.length !== 3) return null;
  var ta = Date.UTC(+pa[0], +pa[1] - 1, +pa[2]), tb = Date.UTC(+pb[0], +pb[1] - 1, +pb[2]);
  if (!isFinite(ta) || !isFinite(tb)) return null;
  return Math.round((tb - ta) / 86400000);
}
function moodOf(e) {
  if (!e || !/^\d{4}-\d{2}-\d{2}$/.test(e.saw || "")) return "cold";   /* 未知 ⇒ 绝不报疏远 */
  var d = dayGap(e.saw, dayKey());
  if (d == null || d <= 0) return "warm";                             /* 未来日期 ⇒ 宁可宽松 */
  return d > COOL_DAYS ? "cool" : "warm";
}
```

配套三件事：

- **写入侧**：`stAdd()` 每次成功互动都会写 `e.saw = dayKey()`（唯一增长入口，无第二条路径）。
- **迁移侧**：`backfillSaw(e)` —— 老档只有 `last` 时，**只有当它落在"过去 0~14 天"这段合理区间**
  才回填 `saw`；范围外（十几年前 / 未来 / 0）一律留空 ⇒ 视为"未知" ⇒ **不报疏远**。
- **读取侧**：日键差 ≤ 0（日期在未来）一律 `warm`。

**三态语义（固化）**：`cold` = 从没互动过（页面不显示任何字）· `warm` = 正常 ·
`cool` = 真的 14 天没来 ⇒ 只说疏远台词、拒绝加好感、**数值一点不掉**（"关系需要维护，但不惩罚"）。

> **教训（值得写进规范）**：任何"多久没来"的判断都必须用**日键**而不是毫秒差。
> 毫秒差在下一次系统时钟被改动时就会变成一颗定时炸弹，而且**首次出现的时机恰好是"刚实装"**，
> 最容易被误读成"新功能有 BUG"。

### 26.2 重整语义（作者问：「重整之后的体力和手牌是怎么样的？」）

源码 `mode/boss.js:1752-1785` 逐行核过。死亡的非魔王角色**每轮**做一个 tick：

```
计数 +1
if (体力 < 上限)      → 回 1 点体力        ← 优先回血
else if (手牌 < 4 张) → 摸 1 张牌          ← 血满了才补牌
if (计数 >= cfg.chongzheng) → revive(当前体力)
```

⇒ **复活体力 = min(重整轮次, 体力上限)**；**手牌 = 死前保留的 + 血满之后每轮补的（补到最多 4 张）**；
**死亡不清手牌**（引擎 die 流程不弃手牌，`content.js:11619` 只把体力归零）。
本次改成 **3/4/5/0** 后（妖灵上限 4）：精英复活 3 血 · 霸主 4 血 · 究极 4 血 + 补 1 张 · 彩蛋永不复活。
**重整对挑战者也生效**，所以改 N 同时改了挑战者的容错。

> ★ 勘误（作者指出）：v6.6 方案初稿写过「3血/4上限让【池悯】的回 1 有了实际作用」——**这是错的**。
> 【池悯】的 +1 上限 / 回 1 / +1 护甲是给**击杀她的那个挑战者**的，与妖灵自己的上限毫无关系；
> 而且它是先 `gainMaxHp(1)` 再 `recover(1)`，**无论对方是否满血都恒生效**。
> 4 上限的真实意义只有一个：妖灵**有效耐久从 3 → 4**（3 血 + 1 甲），并让"差 1 点满血"成为可回复的状态。

### 26.4 濒死链路隔离（本轮新增领域）

作者问：「有些进入濒死触发技能的武将，会不会出现跟魔王技的冲突」。实证后确认**两处真冲突**：

**(a) 挑战者的"观察别人濒死"技被魔王方白嫖。** 名册里 `csh_gongao`（功傲，任何人濒死 → 自己
+1 上限 / 回 1 / 摸 1）与 `csh_daorui`（刀锐，任何人濒死 → 自己 +1 上限）在身份局里是合理的
「队友濒死 = 危机收益」，但在挑战局里**语义整个反了**：魔王濒死是「挑战者即将获胜」的信号，
却白送挑战者成长。
修法：新增 `cshIsBossSidePlayer(p)`——**只在 `lib.config.mode === "boss"` 且 `game.bossinfo` 存在时**
判定 `p.side === true`（挑战局里魔王方 side 恒为 true、挑战者恒为 false），
两技的 filter 追加「濒死者不得属于魔王方」；**其它模式行为零变化**。

**(b) 【反扑】在 dying 里反噬全体挑战者 ⇒ 把 3~4 条濒死链叠在"魔王半死"的上下文里。**
名册共有 **22 个 `player:"dying"` / `global:"dying"` 濒死技**；在 dying 的 content 里连着
`loseHp(1)` 会让挑战者一起进 `_status.dying`，他们的濒死技会在"魔王还没脱离濒死"的时序里
连环触发。修法：`recover(3)` 留在 dying（先救回魔王），**反噬挪到 `dyingAfter`**
（引擎自动末端时点，`library/element/gameEvent.js:213-218` 的 `trigger(name,to)` 会执行
`this.trigger(this.name + trigger2)`，trigger2 ∈ Before/Begin/End/After —— 所以
`dyingBefore → dyingBegin → content → dyingEnd → dyingAfter` 都是真事件），并跳过已濒死者（`hp > 1`）。

**顺带核清、不改**：`csh_rewansha`（完杀）在 `dyingBegin` 给所有人挂封印，
但 `library/skill.js:1634` 的 `skillBlocker = !persevereSkill && !charlotte && !get.is.locked(...)`
⇒ **封印只封非锁定技**；魔王技全员 `locked: true` ⇒ 不受影响，只封妖灵的主动技（百裂/支配/七曜），
属可接受语义。`csh_duwu2`（`dyingAfter`）要求 `evt.name == "csh_duwu" && evt.player == player`
⇒ 只在"自己用该技造成的濒死"触发，无泄漏。

**新增门禁 E29**：钉住两处隔离 + 反扑已拆分 + 反噬段有「跳过已濒死者」守卫。
